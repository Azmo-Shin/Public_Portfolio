# 임베딩 대신 규칙을 고른 이유 — "모른다"를 말할 수 있는 매칭

> 관련 폴더: [07 규칙 기반 스코어링 — D. 매핑코드 자동 부여](../07_rule_based_scoring/)
> 실제 키워드·코드표는 싣지 않습니다.

## 문제: 새 키워드에 기존 코드를 붙이기

메뉴·키워드 원문이 들어오면 기준 코드표의 코드를 자동으로 붙여야 했습니다. 과거에 사람이 붙여 둔 매핑이 있었고, 요즘이라면 자연스럽게 "문장 임베딩으로 가장 가까운 것을 찾자"가 떠오르는 문제입니다.

## 비교해 보니

코드별로 홀드아웃을 떼어 **규칙 매칭**(정규화 → 어휘사전 → exact → 문자열 유사도)과 **한국어 문장 임베딩**을 같은 기준(top-1)으로 비교했습니다. 결과는 규칙이 아주 조금 앞섰습니다. 다만 이 비교에는 단서가 붙습니다. 테스트가 참조 코퍼스와 같은 분포라 문자열 방식에 유리한 **상대 비교**이고, 차이도 작았습니다. 정확도만으로는 결정할 근거가 약했습니다.

## 결정을 가른 것: 틀릴 때의 모양

결정적인 차이는 **틀리는 방식**이었습니다. 임베딩은 코드표에 아예 없는 항목에도 높은 유사도를 내며 그럴듯한 오답을 골랐습니다. 항상 "가장 가까운 것"이 있기 때문입니다. 규칙 쪽은 점수 구간을 나눠 처리를 달리할 수 있었습니다.

- 높은 점수 → 자동 확정
- 중간 점수 → 사람 검수 목록
- 낮은 점수 → **미매칭**(신설 후보)으로 분리

자동 매핑에서 정말 비싼 것은 "모른다"고 말하지 못하는 오답입니다. 한 번 들어간 오답은 다음 회차에 exact 일치로 굳어 버리기 때문입니다. 그래서 확신이 없으면 넣지 않는다는 규칙을 운영 원칙으로 두었습니다.

## 데이터 자체의 함정도 있었다

과거 매핑 CSV 일부가 Excel에서 `-` 로 시작하는 문자열을 수식으로 해석하면서 손상돼 있었습니다(`-값` → `=-값`). 원인을 규명한 뒤, **손상본이 들어오면 멈추는 가드**를 파이프라인 앞에 두었습니다. 매칭 품질보다 먼저 입력 품질을 지켜야 했습니다.

## 배운 점

- 모델 비교는 정확도뿐 아니라 **오답의 모양**(확신에 찬 오답인가, 모른다고 하는가)까지 본다.
- 휴리스틱이면 휴리스틱이라고 부른다. 보고서에도 "규칙 기반"임을 명시했습니다.
- 규칙의 장점은 설명 가능성과 현업이 직접 고칠 수 있다는 점이고, 대가는 **가중치·임계값의 근거를 문서로 남겨야 한다**는 것입니다.
